# REST API

Development base URL: `http://127.0.0.1:8080/api`. The frontend uses `/api` through its development proxy. Request and response bodies use JSON; send `Content-Type: application/json` for `POST` and `PUT`.

The API is unauthenticated and binds to loopback by default. All state is temporary, and AI responses are generated by the local mock provider.

## Health

`GET /api/health` returns `200 OK`:

```json
{
  "status": "UP",
  "provider": "mock"
}
```

This reports application availability; it does not check an external AI service.

## Agents

`GET /api/agents` returns `200 OK` with an array of agent objects. `GET /api/agents/{id}` returns one object, or `404 Not Found` for an unknown ID.

Canonical IDs are `coding-agent`, `documentation-agent`, and `writing-agent`. The list contains these three agents. `translation-agent` and `email-assistant` remain compatibility aliases for reads, updates, and chat. An alias response preserves the requested ID while all three writing IDs read and update the same canonical configuration. Knowledge associated with either legacy agent ID is recognized for the canonical writing agent; a project association alone still grants no agent access.

An agent object has this shape:

```json
{
  "id": "coding-agent",
  "name": "Coding Agent",
  "description": "A thoughtful partner for code, debugging, and architecture.",
  "systemPrompt": "You are a pragmatic senior engineer...",
  "providerId": "mock",
  "modelId": "mock-balanced",
  "temperature": 0.3,
  "maxOutputTokens": 2048,
  "enabledTools": [],
  "ruleIds": [],
  "knowledgeSourceIds": []
}
```

The prompt above is abbreviated for illustration.

### Update an agent

`PUT /api/agents/{id}` updates the editable configuration of an existing agent and returns the updated agent with `200 OK`. Include the original editable fields; the ID comes from the URL. Rule and knowledge assignment lists are optional for backward compatibility.

```json
{
  "name": "Coding Agent",
  "description": "Helps review Java and TypeScript changes.",
  "systemPrompt": "Explain the smallest useful change and its tradeoffs.",
  "providerId": "mock",
  "modelId": "mock-precise",
  "temperature": 0.3,
  "maxOutputTokens": 2048,
  "enabledTools": [],
  "ruleIds": ["coding-rules", "documentation-guidelines"],
  "knowledgeSourceIds": []
}
```

| Field | Validation |
| --- | --- |
| `name` | Required, nonblank, at most 80 characters. |
| `description` | Required, nonblank, at most 500 characters. |
| `systemPrompt` | Required, nonblank, at most 8,000 characters. |
| `providerId` | Required, nonblank, at most 80 characters; currently `mock`. |
| `modelId` | Required, nonblank, at most 80 characters; must belong to the selected provider. |
| `temperature` | Required number from 0 through 2 inclusive. |
| `maxOutputTokens` | Required integer from 64 through 8,192 inclusive. |
| `enabledTools` | Required array of at most 50 unique registered tool IDs. The installed registry is empty, so use `[]`. Enabling a tool does not grant permission to execute it. |
| `ruleIds` | Optional ordered array of at most 50 unique agent-scoped rule IDs. Omitted or `null` preserves current assignments; `[]` clears them. |
| `knowledgeSourceIds` | Optional array of at most 50 unique source IDs explicitly associated with this agent. Omitted or `null` preserves current assignments; `[]` clears them. |

Every assignment ID must be nonblank and at most 80 characters. Agent rule IDs include `coding-rules`, `email-style`, `translation-rules`, `documentation-guidelines`, and the packaged writing rules documented in [Writing & Communication](writing.md). The `global-instructions` rule applies automatically and cannot be assigned explicitly. Unknown or duplicate IDs are rejected before saving; invalid assignments include `errors.ruleIds`, `errors.knowledgeSourceIds`, or `errors.enabledTools` in the HTTP 400 response.

The knowledge metadata repository starts empty; no document-upload or metadata-management endpoint is introduced. A future upload flow must register an agent-associated source before it can be assigned. Project-only associations grant no agent access. General knowledge/tool management and authorization APIs remain future work; writing preset management is available below. See [Module foundations](modules.md).

Updates are shared by later requests during the current backend process. Restarting the backend restores the presets. Creating and deleting agents are outside this phase.

## Chat

`POST /api/chat` accepts:

```json
{
  "agentId": "coding-agent",
  "modelId": "mock-balanced",
  "message": "Help me plan a small REST API."
}
```

Both IDs are required, nonblank strings of at most 80 characters. `message` is required, nonblank, and at most 12,000 characters. The model must be compatible with the agent's provider.

A successful response is `200 OK`:

```json
{
  "id": "34d80c43-76a1-43e4-8fd5-e500872a9856",
  "agentId": "coding-agent",
  "modelId": "mock-balanced",
  "content": "Demo response ... No AI model was called. ...",
  "createdAt": "2026-11-03T09:00:00Z"
}
```

The ID, timestamp, and content above are illustrative. The server creates a response ID and UTC timestamp for each request.

The request's `modelId` selects the model for that message without changing the agent's saved default. The current system prompt and parameters are included in the mock response for inspection. Temperature and output-token settings do not perform sampling or enforce actual token accounting in this implementation.

Execution resolves global/agent rules before constructing the provider request, keeps retrieved excerpts separately classified as untrusted, and passes enabled tool definitions as metadata. The installed retriever returns no excerpts, chat never invokes tools, and the mock provider keeps its existing response templates rather than interpreting instructions. No new chat request fields or response fields are required.

Requests are stateless: previous messages are not submitted to the provider, and the backend stores no conversation history. The UI presents temporary message history for the current local session.

## Writing options and generation

`GET /api/writing/options` returns:

```json
{
  "workflows": [
    {"id":"GENERAL","label":"General writing","supported":true},
    {"id":"EMAIL","label":"Email writing","supported":true},
    {"id":"TRANSLATION","label":"Translation","supported":true},
    {"id":"CV","label":"CV / résumé","supported":false},
    {"id":"COVER_LETTER","label":"Cover letter","supported":false},
    {"id":"JOB_APPLICATION","label":"Job application package","supported":false},
    {"id":"CUSTOM_DOCUMENT","label":"Custom document","supported":true}
  ],
  "presets": [],
  "accounts": [],
  "capabilities": {"generation":"MOCK","sending":false,"recipientDiscovery":"MOCK","attachments":false}
}
```

The example abbreviates `presets` and `accounts`; the running application supplies four initial presets and two mock accounts. Unsupported workflows return HTTP 400 when used for generation or instruction preview. Recipient discovery is a mock port/fixture only: there is no recipient-search REST endpoint or live integration.

`POST /api/writing/generate` accepts a structured writing request:

```json
{
  "workflow": "EMAIL",
  "input": "Kérem, írjon egy udvarias egyeztető levelet.",
  "modelId": "mock-balanced",
  "preferences": {
    "presetId": "friendly-email",
    "inputLanguage": "AUTO",
    "outputLanguage": "DE",
    "translationMode": "NATURAL",
    "formality": "FORMAL",
    "tone": "FRIENDLY",
    "length": "MEDIUM",
    "audience": "A colleague",
    "purpose": "Arrange a meeting",
    "customInstructions": "Keep the draft concise.",
    "selectedRuleIds": []
  },
  "email": {
    "accountId": "mock-personal",
    "recipientName": "Example recipient",
    "to": "recipient@example.invalid",
    "cc": "",
    "bcc": "",
    "subject": "Existing subject",
    "body": "Existing manually edited body",
    "generationPart": "COMPLETE"
  }
}
```

`workflow` defaults to `GENERAL`; `modelId` defaults to `mock-balanced`. Missing preferences default to automatic input language, English output, natural translation behavior, neutral formality, professional tone, and medium length. Missing email fields become empty strings and `generationPart` defaults to `COMPLETE`. Input and email values remain task data; they are not inserted into system instructions. Generation requires nonblank input, or an email body used as a fallback, with at most 12,000 characters.

| Preference | Allowed values or bound |
| --- | --- |
| `inputLanguage` | `AUTO`, `EN`, `DE`, `HU`. Manual overrides are labeled user-selected, not automatically detected. |
| `outputLanguage` | `EN`, `DE`, `HU`, independently selected. |
| `translationMode` | `NATURAL`, `LITERAL`, `PROFESSIONAL`, `REWRITE`, `GRAMMAR`. |
| `formality` | `NEUTRAL`, `FORMAL`, `INFORMAL`. |
| `tone` | `PROFESSIONAL`, `FRIENDLY`, `DIPLOMATIC`, `CONCISE`, `CUSTOM`. |
| `length` | `SHORT`, `MEDIUM`, `LONG`. |
| `presetId` | Empty or an enabled applicable preset ID, at most 80 characters. A `GENERAL` preset may be used for any supported workflow. |
| `audience` / `purpose` / `customInstructions` | At most 500 / 1,000 / 8,000 characters respectively. |
| `selectedRuleIds` | Up to 50 unique existing agent-scoped logical rule IDs. |

Email recipient fields are strings; lists use commas or semicolons. Generation does not validate delivery addresses or send messages. Email field bounds are 80 characters for `accountId`, 200 for `recipientName`, 2,000 each for `to`/`cc`/`bcc`, 500 for `subject`, and 65,000 for `body`. `generationPart: SUBJECT` preserves the exact supplied body; `BODY` preserves the exact subject; `COMPLETE` may replace both. The frontend requires confirmation before replacing manually edited output.

The successful `200 OK` response has this shape:

```json
{
  "id": "generated-uuid",
  "title": "Email writing · demo",
  "content": "DEMO – keine KI-Generierung oder echte Übersetzung. ...",
  "subject": "Demo: Ihre Nachricht",
  "workflow": "EMAIL",
  "detectedLanguage": {
    "language": "HU",
    "confidence": null,
    "mock": true,
    "method": "Demo keyword heuristic; not reliable language detection."
  },
  "outputLanguage": "DE",
  "translationMode": "NATURAL",
  "mock": true,
  "appliedRuleIds": ["global-instructions","writing-core","writing-email"],
  "createdAt": "2026-11-03T10:00:00Z"
}
```

IDs, timestamps, detected language, content, and applied IDs are illustrative; the actual applied-rule array includes all composed rules. Detection may report `EN`, `DE`, `HU`, `UNKNOWN`, or `MIXED`; the heuristic invents no confidence score. Manual language selection has `mock:false` and a user-selected method description. The writing renderer emits fixed labeled language samples and unchanged source text; it performs no translation or Markdown instruction following. Generation does not save or mutate drafts.

`POST /api/writing/preview-instructions` accepts the same request and returns `{ "systemPrompt": "...", "appliedRuleIds": ["..."] }`. It uses the same instruction composer as generation, without including task input, email contents, or retrieved knowledge. It can preview configuration before entering input.

## Writing presets

| Method | Path | Result |
| --- | --- | --- |
| `GET` | `/api/writing/presets` | `200`, array of presets. |
| `POST` | `/api/writing/presets` | `201`, created preset; duplicate IDs return `400`. |
| `PUT` | `/api/writing/presets/{id}` | `200`, updated preset; unknown IDs return `404`. |

Create/update bodies and responses use:

```json
{
  "id":"plain-email",
  "name":"Plain email",
  "description":"Short messages without a greeting or closing.",
  "workflow":"EMAIL",
  "enabled":true,
  "ruleIds":["writing-email"],
  "markdown":"# Plain style\n\nDo not include a greeting or closing.",
  "preferences":{"outputLanguage":"EN","tone":"CONCISE","length":"SHORT"}
}
```

The ID is immutable, starts with a lowercase letter or digit, and contains at most 60 lowercase letters, digits, or hyphens. Name is nonblank with at most 100 characters; description is at most 500; Markdown is nonblank with at most 16,000. `preferences` is optional and defaults as above. `ruleIds` must resolve to agent-scoped rules and may not reference another preset's `writing-user-*` Markdown. Packaged/global/core resources cannot be edited through these endpoints. Markdown is stored as `writing-user-{id}` through the existing rule repository, below immutable instructions in precedence.

Initial IDs are `professional` (`GENERAL`), `friendly-email` (`EMAIL`), `diplomatic-email` (`EMAIL`), and `natural-translation` (`TRANSLATION`). Disabled or incompatible presets cannot be applied. Preset preferences are reusable defaults that the frontend copies into the structured request; the request preferences are the generation service's selected settings. Preset edits and created presets disappear on backend restart. No preset import/export API is implemented.

## Writing drafts

`GET /api/writing/drafts` returns drafts ordered by most recently updated. `GET /api/writing/drafts/{id}` returns one draft or `404`. `POST /api/writing/drafts` creates a snapshot with `201`; `PUT /api/writing/drafts/{id}` updates one with `200`.

```json
{
  "id":"server-assigned-uuid",
  "title":"Reviewed document",
  "workflow":"GENERAL",
  "input":"Original task configuration",
  "content":"Latest manually edited document text",
  "subject":"",
  "preferences":{"outputLanguage":"EN"},
  "email":{"accountId":"","recipientName":"","to":"","cc":"","bcc":"","subject":"","body":"","generationPart":"COMPLETE"},
  "modelId":"mock-balanced",
  "status":"DRAFT",
  "revision":1,
  "updatedAt":"2026-11-03T10:00:00Z"
}
```

The server assigns ID, revision, timestamp, and `DRAFT` status on creation. A nonblank title is required, with at most 200 characters; input, subject, content, preferences, and email have the bounds above (`content` at most 65,000). Update must include the last known numeric `revision`; a missing/stale revision returns `400` with `errors.revision` and preserves current data. Successful updates increment it. Generation never overwrites these snapshots. Frontend edit/version guards additionally protect unsaved changes and per-workflow documents. All drafts are in memory; no deletion endpoint or persistent store exists yet.

## Mock email accounts and delivery preparation

`GET /api/writing/email/accounts` returns account metadata:

```json
{
  "id":"mock-personal",
  "name":"Personal account · mock",
  "email":"personal@example.invalid",
  "provider":"MOCK",
  "connected":true,
  "permissions":["READ_CONTACTS","READ_MESSAGES","MANAGE_DRAFTS"],
  "mock":true
}
```

The response is an array containing this example and an applications account (`mock-applications`, `applications@example.invalid`). Permission order is unspecified. `DELETE /api/writing/email/accounts/{id}` returns `204`, marks the mock account disconnected, and removes its permissions; unknown accounts return `404`. These are demo identities, not connected mailboxes. No OAuth credentials, token endpoints, or password fields exist; ChatGPT account connections are not shared with SAI. `SEND_MESSAGES` is a separate future permission and is absent from mock accounts.

`POST /api/writing/email/preview` takes an **email composition directly**, using the `email` object shape from generation. It validates the selected connected account, at least one `to` address, optional `cc`/`bcc` addresses, and nonblank subject/body. Each recipient field permits at most 50 addresses separated by commas or semicolons; subjects cannot contain line breaks. Syntax validation does not verify an address or grant send authorization.

The immutable snapshot response is:

```json
{
  "id":"preview-uuid",
  "account":{"id":"mock-personal","name":"Personal account · mock","email":"personal@example.invalid","provider":"MOCK","connected":true,"permissions":["READ_CONTACTS","READ_MESSAGES","MANAGE_DRAFTS"],"mock":true},
  "email":{"accountId":"mock-personal","recipientName":"Example recipient","to":"recipient@example.invalid","cc":"","bcc":"","subject":"Reviewed subject","body":"Reviewed body","generationPart":"COMPLETE"},
  "attachments":[],
  "state":"READY_TO_SEND",
  "sendingAvailable":false,
  "mock":true,
  "createdAt":"2026-11-03T10:00:00Z"
}
```

`READY_TO_SEND` describes a validated preparation snapshot; `sendingAvailable:false` still prevents delivery. The current Angular preview displays the exact local draft and retains a Draft label with Send disabled; it does not invoke a delivery integration. Attachments are explicitly planned, with no upload or attachment API.

`POST /api/writing/email/send` accepts `{ "previewId":"preview-uuid", "confirmed":true, "idempotencyKey":"attempt-00000001" }`. False/missing confirmation returns `400`; a valid existing preview and an 8–80 character alphanumeric/hyphen idempotency key are required. **The installed mock connector always rejects sending, even with confirmation.** No request generates a successful mock `SENT` result. The future connector seam checks account connection, independent send permission, connector capability, immutable preview, and duplicate-attempt guards. Preview IDs and duplicate guards are in memory; a production adapter additionally requires authenticated authorization and durable operation records.

Delivery models reserve `DRAFT`, `READY_TO_SEND`, `SENDING`, `SENT`, and `FAILED`. No live sending, OAuth, recipient discovery, or general sensitive-operation approval workflow is implemented.

## Document exports

Exports run entirely in the Angular browser through `DocumentExportService`; there is no export REST endpoint. TXT, PDF, DOCX, and PNG use a captured snapshot of the latest edited title, subject, and content without regeneration. See [Writing & Communication](writing.md) for formatting, pagination, filenames, and browser limitations.

## Errors

Errors use Spring `ProblemDetail` responses, typically with `application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Check the highlighted fields and try again.",
  "instance": "/api/chat",
  "errors": {
    "message": "must not be blank"
  }
}
```

The `errors` map appears for DTO field-validation failures. Validation message text may vary; clients should use the status and field names. Invalid provider/model selections and malformed JSON return `400` with a descriptive `detail`. Unknown agents return `404`. Internal stack traces are not exposed by the application configuration.
