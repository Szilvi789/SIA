# Public source and private personal data

SAI has two independent runtime modes. A public clone contains application code, migrations, generic immutable rules, synthetic seed configurations, and documentation. User-created content is never written back into those resources. Git commands do not run from the application.

## Where data lives

| Data | Demo | Personal |
| --- | --- | --- |
| Agents, model registry, tier mappings, provider flags, usage | Temporary memory with synthetic defaults | Private PostgreSQL tables |
| Personalized Markdown, writing presets, saved drafts | Temporary memory | Private PostgreSQL tables through the existing repositories |
| Conversations | Temporary backend/browser state | Private PostgreSQL; browser restores saved history |
| Knowledge metadata | Temporary memory | Private PostgreSQL |
| Uploaded document bytes | External `demo/uploads` storage adapter | External `personal/uploads` storage adapter |
| Generated exports | Browser-controlled download | Durable external `personal/generated` copy before browser download |
| Backups | No automatic backups | User-managed PostgreSQL/filesystem backups outside Git |
| Credentials and OAuth tokens | Not required | Private configuration files or an appropriate OS credential store; never normal application records |

The upload storage adapter is implemented; a general document-upload HTTP workflow remains future work. Writing exports support TXT, PDF, DOCX, and PNG. In personal mode, their generated bytes are saved with opaque identifiers and validated format extensions. The server never turns a document title or uploaded filename into a filesystem path. Browser download copies use the browser's destination: choose a private folder such as Downloads, outside every checkout. A web application cannot inspect or constrain a browser's Save As destination.

Unsaved edits and message input remain browser memory until saved/submitted. Saved conversations restore from PostgreSQL; the current provider still receives individual tasks, not an automatic full-history prompt. **New conversation** opens a new conversation and retains previous saved history. This feature adds no automatic deletion, synchronization, Git commit, Git push, or Git history rewrite.

## Private filesystem configuration

`SAI_DATA_DIR` is an optional absolute **base** directory outside the repository. The default is `~/.sai/data`, resolved from Java's user-home setting on Windows and macOS. The application always adds a mode namespace:

```text
<SAI_DATA_DIR>/
  demo/
  personal/
    config/
    uploads/
    generated/
    backups/
    rules/
    knowledge/
    conversations/
    drafts/
```

Rules, drafts, conversation content, and knowledge metadata normally use PostgreSQL; their filesystem categories are reserved for explicit future file-based integrations and private exports. No startup import copies private Markdown into `backend/src/main/resources/rules` or another public directory.

Relative paths and paths within the current repository are rejected. Validation resolves existing parents, checks symlinks and containment, and recognizes `.git` directories and worktree `.git` files. Storage keys are opaque UUIDs. Uploads and exports are bounded, validate their declared bytes, and avoid following symlinks. Personal multipart temporary files are also placed in private external storage.

When running a packaged JAR from elsewhere, `SAI_REPOSITORY_ROOT` can identify the source checkout explicitly; the working directory and application code location are checked automatically when available. Do not place private storage in another checkout or cloud-synchronized public folder. No application can identify every unrelated Git repository or control arbitrary user-operated file copies.

New private files request owner-only permissions where the OS supports them. Managed Windows policies may prevent ACL changes; a generic warning reports this without exposing paths or contents. Check inherited Windows ACLs and use a private user directory. macOS uses POSIX owner permissions. Device encryption and appropriately protected backups remain the user's responsibility; this application does not encrypt PostgreSQL volumes or all private files itself.

## Demo mode: clean-clone startup

Demo mode is the default. It uses the existing deterministic mock provider, synthetic agents/presets/models, and generic example rules. No personal database, API key, OAuth account, or private document is required. PostgreSQL connection settings are ignored because demo mode creates no datasource.

Windows PowerShell, from the repository root:

```powershell
$env:SAI_MODE = 'demo'
Set-Location backend
.\mvnw.cmd spring-boot:run
```

In another terminal:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd start
```

macOS:

```sh
cd backend
SAI_MODE=demo sh mvnw spring-boot:run
```

```sh
cd frontend
npm ci
npm start
```

Open `http://127.0.0.1:4200`. The shell shows **DEMO MODE**. Demo changes reset when the backend restarts; frontend unsaved state resets on reload. Generic seed records are explicitly classified as synthetic in personal persistence, while edits are classified as user-owned.

## Personal mode: private PostgreSQL

Personal mode requires all of:

- `SAI_MODE=personal`.
- An external private filesystem base, either the default or `SAI_DATA_DIR`.
- `SAI_DB_URL`, for example `jdbc:postgresql://127.0.0.1:5433/sai_personal`.
- `SAI_DB_USER=sai_personal` when using the provided Compose service.
- `SAI_DB_PASSWORD_FILE`, an absolute path to a small private UTF-8 password file outside the repository.

There is no plaintext database-password environment fallback or API response containing stored credentials. URL userinfo, credential query parameters, schema overrides, and arbitrary JDBC connection hooks are rejected. Personal mode fails startup when its database/configuration is unavailable; it never silently switches to demo memory.

Create the password privately. Example PowerShell setup:

```powershell
$saiPrivateBase = Join-Path $HOME '.sai/data'
$saiConfig = Join-Path $saiPrivateBase 'personal/config'
New-Item -ItemType Directory -Force $saiConfig | Out-Null
$env:SAI_DATA_DIR = $saiPrivateBase
$env:SAI_DB_PASSWORD_FILE = Join-Path $saiConfig 'postgres-password.txt'
if (-not (Test-Path -LiteralPath $env:SAI_DB_PASSWORD_FILE)) {
  $saiRandomBytes = New-Object byte[] 32
  [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($saiRandomBytes)
  [IO.File]::WriteAllText($env:SAI_DB_PASSWORD_FILE, [Convert]::ToBase64String($saiRandomBytes))
}
$saiOwner = [Security.Principal.WindowsIdentity]::GetCurrent().Name
icacls.exe $env:SAI_DB_PASSWORD_FILE /inheritance:r /grant:r "${saiOwner}:(F)"
$env:SAI_MODE = 'personal'
$env:SAI_DB_URL = 'jdbc:postgresql://127.0.0.1:5433/sai_personal'
$env:SAI_DB_USER = 'sai_personal'
docker compose -f compose.personal.yaml up -d postgres
Set-Location backend
.\mvnw.cmd spring-boot:run
```

Check the ACL command's result; organizational policies may block it. The password is never printed. Keep this shell's real configuration outside the checkout. The public `.env.example` is documentation, not an automatically loaded credentials file.

macOS equivalent, from the repository root:

```sh
umask 077
export SAI_DATA_DIR="$HOME/.sai/data"
mkdir -p "$SAI_DATA_DIR/personal/config"
export SAI_DB_PASSWORD_FILE="$SAI_DATA_DIR/personal/config/postgres-password.txt"
if [ ! -f "$SAI_DB_PASSWORD_FILE" ]; then
  openssl rand -base64 32 > "$SAI_DB_PASSWORD_FILE"
fi
chmod 600 "$SAI_DB_PASSWORD_FILE"
export SAI_MODE=personal
export SAI_DB_URL=jdbc:postgresql://127.0.0.1:5433/sai_personal
export SAI_DB_USER=sai_personal
docker compose -f compose.personal.yaml up -d postgres
cd backend
sh mvnw spring-boot:run
```

Start the frontend separately as in demo mode. Docker Desktop must be running. The PostgreSQL service binds only to loopback and keeps its persistent `sai-personal-postgres-data` named volume outside the repository. The Compose definition contains configuration and migration source, not database contents. Do not replace the volume with a bind mount under the repository. `docker compose down` without `--volumes` retains data; volume removal is a separate destructive user action.

Flyway applies additive migrations into the fixed `sai_personal` schema with clean disabled. Dedicated tables store typed JSONB aggregates and ownership markers; parameterized SQL is used. Seed inserts never overwrite existing edits. Draft revisions use atomic PostgreSQL comparisons, and conversation appends serialize per conversation. Demo has neither this datasource nor these persisted tables, so the two modes do not share a database. The browser binds API requests to its discovered mode with `X-SAI-Mode`; the server rejects stale-mode requests before task processing. Switching a connected frontend to another backend mode requires a reload and preserves unsaved browser state until then. Explicit API clients without this optional compatibility header use the selected server's mode.

The personal API currently has no authentication layer and is restricted to loopback. Loopback is not protection from another process or user on the same machine. Do not expose it through a public bind address, proxy, tunnel, or untrusted browser extension.

## Private rules and public examples

Packaged Markdown rules are generic immutable examples/application policy. Personalized writing presets use `RuleRepository.saveUserOwned` and the existing `writing-user-*` namespace. In personal mode, this Markdown is stored in `sai_user_rules`, with preset metadata in its private table. Editing through the UI never changes public resource files. Other private agent instructions and knowledge associations remain private database records. Personalization changes ownership from synthetic to user without rewriting the example source.

## Cloud AI content permissions

Only the mock adapter is installed at present. Personal mode permits future explicitly configured AI/email integrations; it does not install or connect them. Provider metadata or a ChatGPT subscription is not an API credential.

Every installed AI adapter must declare `LOCAL`, `EXTERNAL`, or `UNKNOWN` processing locality. Unknown or missing locality is blocked. Demo mode blocks external generation even if credentials/adapters exist. For an external adapter, personal mode additionally requires:

1. Saved provider-specific permission for task content and personal instructions/preferences.
2. Per-request consent bound to the effective provider.
3. Separate permission for knowledge passages and explicit source IDs for every passage being sent.

The common execution boundary enforces these checks before dispatch, including fallback attempts. Consent for one provider never authorizes another. Local retrieval alone does not authorize sending excerpts externally. Requests contain task content and only the selected, assigned excerpts; the application does not upload the entire private store automatically. Future adapters must maintain these channels and accurately declare endpoint locality.

Settings exposes provider permissions; Chat and Writing expose request consent. Model changes, task edits, and completed generation clear request consent. Saved drafts do not carry reusable consent. Credentials/OAuth tokens belong in external private configuration or an appropriate credential store, not model metadata, public frontend configuration, normal database aggregates, logs, or returned JSON. Request-body and JDBC bind-value logging are disabled in the supplied configuration; do not enable verbose content logging in personal use.

## Git safeguards and publication audit

See [Local privacy audit](privacy-audit.md) for installation and details. Run:

```sh
node scripts/install-privacy-tools.mjs --hooks
node scripts/privacy-audit.mjs
```

The full check combines pinned Gitleaks with path/content checks, scans tracked/staged public files and commit history, and does not print secret matches. Pre-commit examines index blobs; pre-push checks outgoing history so adding then removing a private file does not bypass it. Missing scanner/tool failures block the hooks. GitHub Actions is an additional check after upload; local checks remain essential.

`.gitignore` excludes runtime directories, local environment/configuration, credential material, dumps, and archives while retaining source, generic Markdown, and versioned SQL migrations. Already-tracked files and history are scanned independently of ignore rules. Synthetic binary/document exceptions require an explicit reviewed path, SHA256, and purpose. Plain prose cannot be classified perfectly: review staged Markdown/text and diffs before publication. A clean scan is a safeguard, not proof that no personal information exists.

## Moving from Windows to macOS

Clone only the public source on the Mac, install Java 21, a supported Node.js version, Python for local hooks, and Docker Desktop. Run demo mode and the privacy audit first. Then stop personal writes on Windows, back up PostgreSQL to an external private file using PostgreSQL tools, and copy the private filesystem base through a secure channel. Do not put the backup or private directory in Git, a PR, or a portfolio download.

Restore the database into the Mac's separate private PostgreSQL volume using compatible PostgreSQL versions, set `SAI_MODE`, `SAI_DB_URL`, `SAI_DB_USER`, and the Mac's absolute `SAI_DB_PASSWORD_FILE`, and protect private files with appropriate permissions. Filesystem keys are opaque and database records contain no machine-specific document paths, so the storage base can change. Reauthorize OAuth integrations on the Mac rather than publishing/transferring tokens through the repository. Verify saved rules, drafts, conversation history, and model defaults before retiring the old installation. Keep backups until restore verification succeeds.

Use `npm.cmd`/`mvnw.cmd` on Windows and `npm`/`sh mvnw` on macOS; source line endings are normalized through `.gitattributes`. The directory example uses platform home resolution rather than a committed Windows drive path. macOS execution still needs verification on an actual Mac.
